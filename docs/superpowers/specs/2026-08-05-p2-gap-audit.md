# P2 查漏补缺审计

日期：2026-08-05

目标：对照 `docs/main-roadmap.md`、`docs/MMCE.md` 与当前代码，判断 Phase 2：Requirement / Component 正式层是否已经达到“完美完成”的标准，并列出必须补齐的缺口。

## 1. 结论

P2 尚未完成。当前代码已经实现很多 P2 运行时能力，但存在模型分裂和职责边界不符合 Phase 2 定义的问题，不能把 P2 标记为完成。

- `requirements()` 已成为当前 context 的主要 IO 入口。
- item/fluid/energy 的基本 runtime 路由已存在。
- 多组件聚合、route index、结构化 failure 已有雏形。
- 但 requirement 还没有真正自治，`RecipeCraftingContext` 仍硬编码 item/fluid/energy 细节。
- 代码中存在两套 requirement 类型，语义重复且容易误用。

## 2. 审计依据

- `docs/main-roadmap.md` Phase 2：Requirement / Component 正式层。
- `docs/MMCE.md` 中 `ComponentRequirement`、`RequirementItem`、`RequirementFluid`、`RequirementEnergy`、`ProcessingComponent`、`ComponentSelectorTag` 的语义。
- 既有设计：`docs/superpowers/specs/2026-08-05-phase2-requirement-component-design.md` 与 `docs/superpowers/specs/2026-08-05-phase2-remaining-execution.md`。
- 当前代码：`MachineRecipe`、`RecipeCraftingContext`、`RequirementFailure`、`BlockArray`、`BlockArrayCache`、requirement 相关类与测试。

## 3. 已满足或基本满足

- `MachineRecipe` 已有 `List<MachineRequirement> requirements`，旧 `inputs` / `outputs` / `fluid_outputs` 会派生成 requirements。
- `MachineRecipe.inputs()` / `outputs()` / `fluidOutputs()` 由 requirements 派生。
- `MachineRecipe.CODEC` 已把 `requirements` 作为 stable shape；旧字段 getter 返回空列表，避免编码时重新吐出旧字段。
- item input/output、fluid input/output、energy per-tick 当前 runtime 均从 `recipe.requirements()` 遍历。
- item/fluid route 已按 requirement index 建立。
- commit 前有 item/fluid input/output route 验证，避免部分 route 先 mutation。
- `RequirementFailure` 已包含 requirement index、kind、required、available、shortAmount、searchedComponents、matchedComponents。
- `BlockArray` 已有 `tagsByPosition`、`tagged(pos, tags...)`、`tagsAt(pos)`。
- `BlockArrayCache.rotate()` 会同步旋转 tags。
- `ProcessingComponent` 已支持 `List<String> tags`，并保留 legacy single-tag getter。

## 4. 必须纳入 P2 的端口要求

如果需求是“配方至少需要多少输入/输出端口才能运行”，它应归入 Phase 2：Requirement / Component 正式层。

- Phase 2 的目标是从简化 `MachineIngredient` 模型过渡到接近 MMCE 的 requirement/component 路由模型。
- Phase 2 验收要求多个同类输入能跨多个组件聚合，而不是只找第一个 bus/hatch。
- Phase 2 验收要求 `ProcessingComponent` 可按 component type、IO type、selector tag 过滤。
- 因此 recipe runtime 层面的“需要几个 input bus / output bus / hatch 才能运行”应由 Phase 2 requirement/component 层表达。
- 这不同于 P1 的“结构成型时识别端口数量 / 端口是否在 matched pattern 内”。P1 管结构成型与组件收集，P2 管 recipe 运行时组件需求与路由。

## 5. 未满足：Requirement 模型分裂

当前有两套 requirement 类型：

- 旧行为接口：`cn.howxu.mmcr.api.recipe.MachineRequirement`，包含 `matches` / `simulate` / `commit` / `ioTick`，以及旧包下 `ItemRequirement`、`FluidRequirement`、`EnergyRequirement`。
- 新数据模型：`cn.howxu.mmcr.api.recipe.requirement.MachineRequirement`，只包含 `type()`、`io()`、`tags()`，以及新包下 record `ItemRequirement`、`FluidRequirement`、`EnergyRequirement`。

实际 `RecipeCraftingContext` import 的是新包 requirement，但还保留 `Map<cn.howxu.mmcr.api.recipe.MachineRequirement, List<?>> routes`、`componentsMatching(cn.howxu.mmcr.api.recipe.MachineRequirement)`、`route(cn.howxu.mmcr.api.recipe.MachineRequirement, ...)` 等旧行为接口入口。

必须补齐：删除或迁移旧 `api.recipe.MachineRequirement` 体系，避免两个同名概念长期并存。推荐保留 `api.recipe.requirement.*` 作为唯一 public requirement 包，并把需要的行为方法迁入它；或者把旧行为接口改造成唯一接口并删除新重复 records。二选一，不能继续并存。

## 6. 未满足：Requirement 还未自治

P2 设计要求：`MachineRequirement` 自己负责匹配组件、simulate、commit、output、per-tick IO；`RecipeCraftingContext` 负责上下文和 route 缓存。

当前实现相反：`RecipeCraftingContext.simulateInputs()` / `simulateOutputs()` / `commitInputs()` / `commitOutputs()` 仍直接 `instanceof ItemRequirement / FluidRequirement / EnergyRequirement`，并在 context 内部构造 `MachineIngredient.ItemIngredient` / `FluidIngredient` 来复用旧 helper 状态。

必须补齐：把 item/fluid/energy 的 `matches`、simulate route 建立、commit route 验证/执行、ioTick 行为下沉到唯一的 requirement 类型；context 只提供组件查询、route 保存、failure 写入等通用能力。

## 7. 未满足：Context 仍具体 BE 化

P2 验收要求 context 不直接依赖具体 BE 类，优先依赖 component/container 接口。当前 `RecipeCraftingContext` 仍大量直接引用：

- `ItemInputBusBlockEntity` / `ItemOutputBusBlockEntity`
- `FluidInputHatchBlockEntity` / `FluidOutputHatchBlockEntity`
- `EnergyInputHatchBlockEntity`

必须补齐：把具体 BE 判断集中到 component adapter 或 requirement 内部的容器解析层。context 层不应散落按 BE class 的 `liveComponents(...)`、`itemInputStates(...)`、`fluidOutputStates(...)` 等逻辑。

## 8. 未满足：Selector Tag Failure 语义不完整

tag 匹配基础逻辑已存在：requirement tag 空则通配，component tags 空且 requirement tags 非空则不匹配，两边都有 tag 则任一重叠即命中。

但当前缺口：

- `RequirementFailure.Kind.TAG_MISMATCH` 已定义，但没有在 `RecipeCraftingContext` 中实际使用。
- 当存在同类组件但全被 tag 排除时，failure 仍会表现为 generic missing input/output，无法区分“数量不足”与“tag 选错”。
- 目前测试只覆盖 item tag route 成功，不足以覆盖 wrong-tag failure、fluid tag route、BlockArray tag 经结构匹配进入 `updateComponents()` 的 E2E。

必须补齐：在候选过滤时保留“同类但 tag 不匹配”的 searched traces；如果同类组件存在但 tag 全不命中，写 `TAG_MISMATCH`，同时保持 `lastFailureUnloc` 兼容现有 UI 文案。

## 9. 未满足：旧 Runtime Helper 和 Dead API 未清理

`RecipeCraftingContext` 中还存在旧行为接口相关 route map 和 `componentsMatching(...)`。`api.recipe.ItemRequirement` / `FluidRequirement` / `EnergyRequirement` 旧类仍在源码中存在，但当前主 runtime 使用新包 records。

必须补齐：清理未被主路径使用的旧类和方法，或把它们合并为唯一实现。保留 dead API 会让后续 Phase 3 modifier、Phase 4 JEI、Phase 5 parallel 接错类型。

## 10. P2 完美完成前的强制补缺清单

按优先级执行：

1. 统一 requirement 包和接口：只保留一套 `MachineRequirement` / `ItemRequirement` / `FluidRequirement` / `EnergyRequirement`。
2. 把 `matches/simulate/commit/ioTick` 迁入唯一 requirement 类型，context 只做通用调度和 route/failure 存储。
3. 删除 `RecipeCraftingContext` 中旧 `api.recipe.MachineRequirement` route map、`componentsMatching(...)` 与旧包 requirement 类，或把它们改成唯一实现的一部分。
4. 将 context 的具体 BE 依赖收敛到 component/container adapter，至少不要在 context 主流程中散落 item/fluid/energy BE 分支。
5. 完成 selector tag 的 wrong-tag failure：同类组件存在但 tag 全不匹配时产出 `RequirementFailure.Kind.TAG_MISMATCH`。
6. 补测试：wrong-tag item failure、wrong-tag fluid failure、BlockArray tag 经 `BlockArrayCache` + `MachineControllerBlockEntity.updateComponents()` 到 runtime route 的集成路径。
7. 更新 `docs/main-roadmap.md` 当前基线：P2 只能在以上补缺后标为完成。

## 11. P2 验收门槛

- `./gradlew compileJava --no-daemon` 通过。
- `./gradlew test --no-daemon` 通过；如 GameTest 环境不可用，需要记录未跑原因。
- 源码中只剩一套 requirement 类型；不存在两个包下同名 requirement 概念。
- `RecipeCraftingContext` 不再直接遍历 `recipe.inputs()` / `recipe.outputs()` / `recipe.fluidOutputs()` 作为 runtime 主路径。
- `RecipeCraftingContext` 不再持有旧 `api.recipe.MachineRequirement` route map。
- item/fluid/energy runtime 均由 requirement 分派，并且 commit 只使用 simulate route。
- selector tag 成功和失败路径都有测试，失败能区分 missing 与 tag mismatch。
- output 空间不足、route invalidation、energy per-tick failure 不会吞输入。

## 12. 当前可接受的状态标记

Phase 2 只能标记为“功能大半落地，但架构未闭环；不得标记完成”。
