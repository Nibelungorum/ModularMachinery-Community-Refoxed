# P1 查漏补缺审计

日期：2026-08-05

目标：对照 `docs/main-roadmap.md`、`docs/MMCE.md` 与当前代码，判断 Phase 1：核心运行时闭环是否已经满足路线图要求，并记录必须保留在 P1 的验收口径。

## 1. 结论

P1 已基本完成，但最终仍需要全量测试或 GameTest 复核后才能在路线图中标记为完全完成。

- 结构成型后使用结构内组件执行配方的主路径已落地。
- 控制器已从 matched pattern 收集端口组件，而不是扫描固定范围。
- item/fluid/energy input/output 端口已能作为 recipe runtime 组件参与结构内 IO。
- failure action、per-tick energy、item/fluid output 的核心闭环已落地。
- “多方块成型时识别结构内端口 / 端口数量检测”归属 P1 / 2.1 结构组件上下文，不应推到 JEI 或高级组件阶段。

## 2. 审计依据

- `docs/main-roadmap.md` Phase 1：核心运行时闭环，尤其 2.1 结构组件上下文。
- `docs/MMCE.md` 中 `MachineComponentTile`、`MachineComponent`、`ProcessingComponent`、`BlockArray`、`TaggedPositionBlockArray`、`DynamicPattern` 的语义。
- 当前代码：`MachineControllerBlockEntity`、`ProcessingComponent`、`RecipeCraftingContext`、`ActiveMachineRecipe`、`BlockArray`、`BlockArrayCache`。

## 3. 已满足项

- `MachineControllerBlockEntity.updateComponents()` 遍历 `foundPattern.pattern().keySet()`，只收集 matched pattern 内的 `MachineComponentTile`。
- `updateComponents()` 把 `provideComponent()`、world pos、relative pos、`foundPattern.tagsAt(relativePos)` 写入 `ProcessingComponent`。
- `resetMachine()` 清空 `foundMachine`、`foundPattern`、`components`、`active`、`context`、paused active/context、failure 状态和 formed/active state。
- `serverTick()` 每 tick 先 `checkStructure()`，只有 formed 后才 `tryStartNewRecipe()` / `tickActiveRecipe()`。
- `ActiveMachineRecipe.tick(context)` 在完成前调用 `context.ioTick(recipe)`；失败时按 `context.failureAction()` 执行 `RESET/STILL/DECREASE`。
- `RecipeCraftingContext.ioTick()` 当前从 `recipe.requirements()` 找 `EnergyRequirement` 并逐 tick 消耗结构内 energy input hatch。
- `simulateOutputs()` / `commitOutputs()` 覆盖 item output 与 fluid output；output 不足时不会启动 recipe，因此不会吞输入。
- `MachineRecipe.assemble()` 返回首个 item output；fluid-only recipe 返回 `ItemStack.EMPTY`。

## 4. 必须纳入 P1 的端口要求

结论：端口识别类 feat 在 `main-roadmap.md` 里最接近 Phase 1：核心运行时闭环 / 2.1 结构组件上下文，不是 JEI 或高级组件阶段。

- Phase 1 的目标是“结构成型后使用结构内组件执行配方”，并明确要从 matched pattern 收集端口组件，而不是扫描固定范围。
- “多方块成型时识别结构内端口”属于 P1 / 2.1 的结构组件上下文。
- Phase 1 的验收标准包括：成型后日志能列出 item input/output、fluid input/output、energy input/output 数量。
- Phase 1 的验收标准还包括：pattern 内端口可用，pattern 外端口不能误用。
- 因此“端口数量检测”最早应落在 P1，而不是 Phase 4 JEI 或 Phase 5+ 高级组件阶段。

## 5. P1 与 P2 的边界

如果需求是“多方块至少需要多少端口才允许成型”，它应归入 P1 / 2.1，因为这是结构成型门槛。

如果需求是“某条 recipe 至少需要多少输入/输出组件才能运行”，它应归入 P2，因为这是 runtime requirement/component 路由问题。

当前文档中没有把“最低端口数才成型”作为 MMCE 独立 feat 明确列出。MMCE 的结构成型基础是 `BlockArray.matches(...)` 按结构位置匹配方块，端口作为 `MachineComponent` 的 ItemBus / FluidHatch / EnergyHatch 存在。

`DynamicPattern` 的 `minSize/maxSize` 是动态结构段数，不是端口数量限制。

## 6. 仍需注意但不阻塞 P1

- `RecipeCraftingContext` 目前仍直接依赖具体 BE 类型。这属于 P2 “context 去具体 BE 化”的目标，不应回头算作 P1 blocker。
- active recipe NBT restore 后 `context = new RecipeCraftingContext(this)`，组件依赖下一次 server tick 的 `checkStructure()` 刷新。当前 tick 顺序可以覆盖，但建议保留 GameTest 覆盖“重载后结构组件仍可继续 tick”。
- P1 完成前应至少跑 `./gradlew compileJava --no-daemon` 与 `./gradlew test --no-daemon`；GameTest 若不可用，需要记录原因。

## 7. P1 完成定义

- matched pattern 内组件被收集到 `ProcessingComponent`。
- pattern 内端口参与 recipe IO，pattern 外端口不能参与。
- 成型后能统计 item/fluid/energy input/output 数量。
- 结构 reset 会清空 components、active recipe、context 和 failure 状态。
- per-tick energy 和 failure action 按 P1 语义工作。
- item/fluid output 空间不足时不启动 recipe，不吞输入。
