# 动态机器与配方重载设计

## 目标

使 MMCR 的运行期机器定义和运行期机器配方具备可重载的基础架构，并提供统一的重载服务供原版 `/reload` 和 `/mmcr reload` 使用。

本设计为尚未迁移至 Minecraft 26.1.2 的 KubeJS 兼容层预留接入点，不实现或测试 KubeJS 重载。KubeJS 可用后，动态机器和配方将通过该接入点参与重载。

## 范围

包含：

- 将机器定义和机器配方区分为静态/API 来源与可替换的动态来源。
- 在不破坏现有查询 API 的前提下，让注册表对外提供两个来源的合并视图。
- 增加能原子替换动态快照并重建运行时缓存的服务。
- 将 `/mmcr reload` 改为只刷新 MMCR 动态内容，不触发原版数据包重载。
- 为原版 `/reload` 预留在其数据包与 KubeJS server script 重载完成后调用同一服务的 Mixin 接入点。
- 提供动态机器删除的命令反馈，说明其控制器注册表对象会在下一次服务端启动后才消失。

不包含：

- KubeJS 的实现、依赖、Mixin、自动化测试或运行期调用。
- 控制器 BlockState、模型、贴图、翻译键与客户端资源的动态重载。
- 在运行中的 NeoForge 注册表里注销控制器方块、方块物品或方块实体。
- 让原版 `RecipeManager` 承载 MMCR 内存机器配方。原版数据包配方仍按原版 `/reload` 的既有生命周期重载。

## 当前约束

`MachineDefinitions` 目前承载启动期控制器注册所需的定义，`MachineRegistry` 持有机器及已编译结构缓存，`RecipeRegistry` 持有按机器索引的内存配方。三者目前均是单一可变映射，KubeJS 构建器会直接写入它们。

控制器 Block、BlockItem 和 BlockEntity 是 NeoForge 启动期注册表对象。动态机器定义删除后只能从 MMCR 的运行期匹配与配方查询中移除，不能在不重启服务端的情况下从原版注册表中安全删除。

## 架构

### 来源分层

每个相关注册表维护两层内容：

- 静态/API 层：内置机器、普通 API 注册的机器以及其配方。生命周期为服务端进程，不受动态重载影响。
- 动态层：当前有效的运行期快照。未来仅由 KubeJS 等显式动态来源写入，可整体替换。

对外查询维持现有方法和语义：`MachineDefinitions.get/all`、`MachineRegistry.getMachine/getAll/getCompiled`、`RecipeRegistry.getRecipe/recipes/byMachineId` 返回静态层与动态层的合并结果。相同 ID 与静态层冲突视为候选快照非法，不能覆盖静态/API 内容。

### 候选会话与提交

新增一个动态内容重载服务，负责以下状态转换：

1. 开始重载时创建空的候选会话，候选会话包含机器与配方的有序映射。
2. 动态来源在会话内注册机器和配方；验证重复 ID、与静态层冲突以及配方引用的机器是否存在于静态层或当前候选机器中。
3. 所有来源成功完成后，服务一次性以候选内容替换动态层。
4. 提交后重建 `MachineRegistry` 的编译结构缓存，刷新 `RecipeCraftingContextPool`，并增加配方重载版本。
5. 任何来源报告失败时丢弃候选会话，不修改当前动态层和运行时缓存。

候选会话只在服务端主线程创建、写入和提交。提交前不更新任何全局查询结果，因此脚本中途失败不会暴露部分机器或配方。

未来 KubeJS 接入后，`MachineBuilderJS.registerObject()` 与 `MachineRecipeBuilderJS.build()` 写入活动候选会话，而非直接修改全局注册表。配方构建器解析机器时优先查询候选机器，再查询静态/API 层，以支持同一脚本中先注册机器、后注册配方。

## 命令与时序

### `/mmcr reload`

命令要求管理员权限，仅重载 MMCR 动态内容：

1. 请求动态内容来源生成候选会话。
2. 所有来源成功时提交快照并刷新结构、配方运行时缓存。
3. KubeJS 未接入期间，该命令提交空动态快照并只刷新 MMCR 缓存；不会执行原版数据包重载。
4. 完成后向命令执行者报告机器与配方的新增、更新、删除数量。

KubeJS 迁移完成后，该命令会完整重载 KubeJS server scripts。KubeJS 脚本全部成功后才提交候选快照；任意脚本错误则保留上一份有效动态快照并向执行者报告失败。

### 原版 `/reload`

原版 `/reload` 继续负责数据包及原版 `RecipeManager` 重载。未来通过最小 Mixin 在 KubeJS server script 重载成功完成后调用动态内容重载服务提交候选快照。MMCR 不复制原版 `/reload` 的实现，也不替换 KubeJS 的脚本管理器。

当 KubeJS 脚本失败时，原版数据包重载的结果保持由原版/KubeJS 决定；MMCR 仅拒绝提交自己的候选快照，继续使用上一个有效动态快照。

## 删除语义

提交前后比较动态机器 ID：

- 不再存在于新快照的机器立即从 `MachineRegistry`、已编译结构、机器配方查询和后续结构匹配中移除。
- 已放置的对应控制器方块不会从世界中移除，但因为其机器定义不再可查，不能再形成或运行该机器。
- 控制器 Block、BlockItem、BlockEntity 的注册表项继续保留，直到下次服务端启动；此限制会逐个 ID 反馈给命令执行者。

命令反馈仅发送给执行命令的 `CommandSourceStack`。没有删除时不输出重启提示。

## JEI 与同步边界

动态快照提交是 JEI 刷新的唯一触发点。提交结果必须提供变更集，以便未来 JEI 兼容层能够向客户端同步 MMCR 动态配方视图，并刷新 MMCR 的 JEI 分类。

本设计不实现 JEI 客户端刷新，也不假设 KubeJS 已经可用。实施时应以当前 JEI 集成的实际注册和刷新 API 决定最小同步方式；不得通过全量客户端资源重载解决配方视图更新。

## 错误处理

- 静态/API ID 冲突、候选内重复 ID、配方指向未知机器、非法机器或配方均使本轮候选会话失败。
- 失败原因应记录到 MMCR 日志，并作为简短失败信息返回给命令执行者。
- 失败时不清空动态层，不重建基于候选内容的缓存，也不触发 JEI 变更通知。
- 无动态来源或空候选快照是有效结果，可删除上一轮全部动态内容；该结果必须由成功完成的来源显式提交，不能由来源加载失败隐式产生。

## 验证

本阶段不为 KubeJS 编写测试，因为该兼容层尚未迁移到 26.1.2。

非 KubeJS 的单元测试应覆盖：

- 静态/API 与动态层的合并查询和 ID 冲突拒绝。
- 候选会话的原子提交与失败回滚。
- 动态机器删除后结构编译缓存和机器配方索引不再包含该 ID。
- `/mmcr reload` 不调用原版数据包重载，并只刷新 MMCR 运行时缓存。

JEI 刷新和 KubeJS 完整 reload 在对应兼容层迁移后补充集成测试与客户端手工验证。

## 后续工作

客户端控制器的方向、模型、贴图和翻译键动态表现独立设计。该工作需要处理方块状态定义和资源重载边界，不能与本服务端动态快照方案混为同一个提交。
