# 动态控制器客户端表现设计

## 目标

使启动期预留的机器控制器能在服务端动态机器重载后使用新的控制器规格显示。客户端不运行 KubeJS 脚本，而是接收服务端同步的控制器规格快照。

## 范围

包含：

- 通用控制器模型按机器 ID 在运行期解析 `MachineControllerSpec`。
- 服务端同步完整的机器 ID 到控制器规格快照。
- 玩家登录、切换维度和 MMCR 重载成功后替换客户端快照。
- 清理模型缓存并重渲染控制器方块。
- 保留 `FACING`、`ROLL_FACING`、`FORMED` 和 `ACTIVE` 状态属性。
- 对删除机器、未知机器 ID 与无效同步包安全降级。
- 控制器物品渲染路径查询同一份机器 ID 到规格映射。

不包含：

- 翻译键、语言文件或本地化内容。
- 贴图和模型资源的生成、分发、存在性校验或资源包加载。
- 服务端发送 PNG、模型 JSON 或语言文本。
- 运行期新增或移除 NeoForge Block、BlockItem、BlockEntity 注册表对象。
- 运行期修改方块 `StateDefinition`。
- KubeJS 26.1.2 迁移或 KubeJS 自动化测试。

## 当前基础

`MachineControllerBlock` 按机器 ID 创建，并始终声明 `FACING`、`ROLL_FACING`、`FORMED` 和 `ACTIVE`。`MachineControllerSpec` 已包含前、侧、顶、底四个纹理 `Identifier` 与纵向、旋转相关标志。现有 `ModelGen` 在数据生成期从规格生成每台控制器的静态模型，所以运行期修改规格不会改变已烘焙模型。

控制器 Block、BlockItem 和 BlockEntity 都在 `ModBlocks`、`ModItems` 与 `ModBlockEntities` 的启动期注册。NeoForge 注册表不能在服务端运行时安全地新增或删除这些对象。

## 启动期预留

KubeJS `startup_scripts` 声明机器 ID 并预留控制器。启动期为每个 ID 创建控制器 Block、BlockItem 和 BlockEntity 映射。之后 `server_scripts` 只能替换已预留 ID 的机器结构、配方和控制器规格，不能首次注册未知控制器。

服务端提交动态机器快照前必须验证每个动态机器 ID 存在预留控制器映射。验证失败时拒绝整个候选快照，保留之前的服务端动态内容和客户端同步内容。

机器删除只从运行期机器和同步快照移除规格。已注册且已放置的控制器对象继续存在；找不到规格的客户端控制器使用默认外观。

## 通用动态模型

所有预留控制器引用同一个通用模型入口。模型解析时从 `MachineControllerBlock.machineId()` 获取机器 ID，在客户端规格缓存中查询 `MachineControllerSpec`，并用规格中的四个纹理标识构造或查找基础面与覆盖层变体。

通用模型必须服务于世界方块、控制器物品、方块破坏粒子和掉落物。世界渲染可从方块直接取得机器 ID。物品渲染没有方块实体，因此 BlockItem 必须通过注册映射或等价模型上下文保存机器 ID，使背包、创造栏和 JEI 也能查询同一缓存。

纹理 Identifier 是透明数据。MMCR 不校验资源是否存在；缺失资源交由原版 missing texture 处理。

## 朝向

BlockState 继续保存并传递 `FACING`、`ROLL_FACING`、`FORMED` 和 `ACTIVE`。动态重载不重建状态定义，也不改写世界中的已有状态。

通用模型按 `FACING` 与 `ROLL_FACING` 旋转。`allowVerticalFacing`、`fullyRotationallySymmetric` 和 `requireVerticalFacing` 决定后续放置与服务器结构匹配的有效规则，但不会修正旧方块的朝向。新规格不再允许的旧朝向会在服务端被视为无法形成结构，而客户端仍按存储状态正常显示。

## 服务端同步

新增只同步数据的控制器规格快照包，载荷为有序的 `Identifier -> MachineControllerSpec` 映射。包不携带模型、贴图或翻译资源。

服务端在以下时机向目标玩家发送完整快照：

- 玩家登录并完成客户端可接收 play payload 的阶段。
- 玩家切换维度后。
- MMCR 动态机器快照成功提交后，向所有在线玩家发送。

使用完整快照而不是增量包。动态机器数量相对有限，完整替换避免客户端在漏包、删除和重连后维护复杂的增量状态。

服务端仅将当前仍有机器定义且具有预留控制器的控制器规格加入包。静态机器和当前动态机器都包含在快照中，使客户端不依赖本地脚本或本地定义注册顺序。

## 客户端缓存与失效

客户端维护不可变规格映射和由“机器 ID + 规格值”定位的通用模型变体缓存。收到包时先完整解码和验证，再一次性替换规格映射；验证失败则丢弃整包、保留旧缓存并记录日志。

成功替换时：

1. 清空通用控制器模型变体缓存。
2. 通知模型管理器重新解析通用控制器模型。
3. 标记已加载区块中所有 `MachineControllerBlock` 为需要重渲染。
4. 使控制器物品模型缓存失效，确保背包、创造栏和 JEI 后续渲染使用新规格。

删除机器时，新快照不含对应 ID。模型查询未命中时使用 `MachineControllerSpec.defaultsFor(machineId)` 与默认控制器模型外观；不得返回空模型或抛出渲染异常。

## 错误处理

- 服务端候选快照包含未预留控制器 ID：拒绝提交，保留旧服务端和客户端可见内容。
- 客户端包包含重复 ID、空 ID、空规格或无效字段：拒绝整个包，保留上一份有效快照。
- 客户端缓存未含某机器 ID：使用默认规格。
- 客户端资源缺失：不干预原版资源系统。

## 验证

- 单元测试：快照编解码、完整替换、无效包回滚、删除 ID 的默认规格降级、预留 ID 验证。
- 客户端测试：模型变体缓存按快照替换失效，方块和物品均从机器 ID 解析规格。
- GameTest：动态机器删除后，已放置控制器仍存在但服务端不再形成结构。
- 手工客户端验证：重载后已有控制器的规格标识改变，水平和纵向摆放，重连后的同步，以及删除机器后的默认外观。

## 后续边界

本设计依赖动态机器与配方重载服务提供成功提交事件和当前合并机器快照。KubeJS 迁移后，startup script 的预留声明和 server script 的候选定义写入接入这些边界；客户端仍无需执行 KubeJS 脚本。
